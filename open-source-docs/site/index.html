ETRI Internal · Documentation

연구 실험을 부탁하면, 실행부터 증거까지.

mini-science-ai-os는 연구자가 복잡한 Kubernetes 명령을 직접 다루지 않고도 CPU·GPU 실험을 제출하고, Queue 상태와 Kubeflow 실행, Metric과 Artifact를 한 흐름으로 확인하게 해 주는 ETRI 내부 연구 플랫폼입니다.

현재 제품 범위

단일 Kubernetes 클러스터의 tenant-etri 전용 내부 MVP입니다. 실제 Federation, SLURM·Cloud 실행, 중앙 SSO와 외부 TLS 서비스는 아직 범위 밖입니다.

연구 놀이터 이야기

연구자 민지가 인공지능 실험을 하고 싶다고 생각해 봅시다. 원래는 빈 컴퓨터를 찾고, GPU 사용자를 확인하고, 실행 명령과 저장 위치까지 직접 관리해야 합니다. Science AI OS는 이 일을 여러 전문 도우미에게 나눠 줍니다.

연구자는 “이 실험을 해 주세요”라고 신청합니다. 접수 선생님은 위험한 부탁이 아닌지 검사하고, 번호표 기계는 자원이 생길 때까지 순서를 지킵니다. 자리 배정 선생님이 컴퓨터를 고르면 프로그램이 실행되고, 실험 공책과 창고가 숫자 결과와 파일을 보관합니다.

버튼을 누른 뒤 일어나는 일

  1. Workspace에서 프로젝트, 이미지, 명령, CPU·Memory·GPU를 입력합니다.
  2. Science Job API가 Tenant, Registry, 자원 상한과 위험한 입력을 검사합니다.
  3. Kubeflow Pipelines가 Run과 실행 이력을 만듭니다.
  4. Kueue가 Quota를 확인하고 실행 가능 여부를 결정합니다.
  5. Scheduler와 HAMi가 Node와 논리 GPU 몫을 배정합니다.
  6. Kubernetes Job이 제한된 권한으로 Container를 실행합니다.
  7. MySQL·Metadata와 MinIO가 실행 색인과 Artifact를 보관합니다.
  8. 사용자는 Workspace에서 상태, Metric과 Artifact를 다시 확인합니다.
Pending은 항상 실패가 아닙니다

Quota나 자원이 부족하면 Kueue가 작업을 버리지 않고 기다리게 합니다. Workload의 Condition에서 정확한 대기 사유를 확인할 수 있습니다.

CPU와 GPU

CPU는 여러 종류의 일반 계산을 잘하는 일꾼입니다. GPU는 비슷한 계산을 한꺼번에 많이 처리하는 데 강합니다.

HAMi는 한 물리 GPU를 여러 Job이 논리적으로 공유하도록 Memory와 Core 비율을 표시합니다. 예를 들어 GPU Memory 1024MiB와 Core 10%를 요청할 수 있습니다.

논리 할당과 성능 보장은 다릅니다

HAMi Annotation이 논리 몫을 보여 주더라도 실제 처리량과 메모리 대역폭이 완전히 격리된다는 뜻은 아닙니다. DCGM Metric과 함께 관찰해야 합니다.

Queue와 Quota

Queue는 실행 차례를 기다리는 줄이고, Quota는 한 팀이 사용할 수 있는 최대 자원입니다. tenant-etri의 LocalQueue는 공용 science-shared ClusterQueue에 연결됩니다.

bash · Kueue state
kubectl get localqueue -n tenant-etri tenant-etri
kubectl get clusterqueue science-shared
kubectl get workloads -n tenant-etri

Metric과 Artifact

Metric은 accuracy, loss, duration처럼 숫자로 비교하는 성적표입니다. Artifact는 모델, 그래프, 결과 표처럼 파일로 남는 작품입니다.

Kubeflow가 Run과 Parameter·Metric을 연결하고, MinIO가 결과 파일을 보관합니다. 사용자는 Workspace의 Job 상세 또는 Kubeflow UI에서 이를 확인합니다.

MCP Agent

MCP Runtime은 사람 대신 Science Job API에 부탁하는 제한된 도우미입니다. 자율 Cluster 관리자가 아닙니다.

보안 경계

  • Tenant, Namespace, ServiceAccount와 Queue는 서버 설정으로 ETRI에 고정됩니다.
  • Portal은 내부망의 ETRI 고정 HttpOnly Session을 사용하고, 직접 API와 MCP는 Token을 요구합니다.
  • Job은 non-root, read-only root filesystem, RuntimeDefault seccomp와 Capability drop ALL을 적용합니다.
  • Secret은 Kubernetes Secret에 두며 Portal HTML과 Git에 포함하지 않습니다.
  • privileged, hostPath, hostPID, hostNetwork와 임의 ServiceAccount 입력을 받지 않습니다.

알려진 한계

내부망 전용

현재 TLS와 개인별 OIDC 로그인이 없습니다. 승인된 내부망 밖으로 공개하면 안 됩니다.

  • 실제 다기관 Federation과 Site Scheduling
  • 실제 SLURM 제출과 Cloud Adapter
  • 개인별 Agent Identity와 승인 Gate
  • Flannel 환경의 NetworkPolicy Enforcement 증명
  • 원격 Backup과 Disaster Recovery
  • GPU 물리 성능 격리 보장

자주 묻는 질문

이것은 단순 화면 모형인가요?

아닙니다. 현재 내부 Kubernetes Cluster에서 API, MCP, KFP, Kueue와 MinIO가 실제로 실행 중인 단일 Tenant MVP입니다.

Pending이면 실패한 건가요?

아닐 수 있습니다. Kueue가 Quota나 자원을 기다리게 하는 정상 상태일 수 있으므로 Workload Condition을 확인합니다.

GPU 10%면 성능도 정확히 10%인가요?

아닙니다. HAMi의 Core와 Memory 값은 논리 할당입니다. 실제 처리량과 대역폭 격리는 별도 검증이 필요합니다.

인터넷에 공개해도 되나요?

안 됩니다. 현재 TLS와 개인별 OIDC 인증이 없는 trusted-network 내부 제품입니다.
