## 발견한 문제와 조치

- 첫 server-side apply에서 기존 `kubectl` field manager와 충돌했다. 강제 소유권 이전 없이 기존 client-side apply 방식으로 적용했다.
- Chromium에서 프로젝트 `pattern`의 `v` 정규식 규칙 경고를 발견해 하이픈을 escape했다.
- favicon 404와 Password Form username 경고를 제거했다.
- KFP 실패 Run이 Kubernetes Job 성공으로 보일 수 있어 KFP 실패를 우선하는 통합 상태를 적용했다.
- `submitting`의 순간 상태가 `neutral`로 보이는 문제를 `제출됨`으로 매핑했다.
- 설명 사이트를 plain `-f`로 갱신하면 생성 ConfigMap이 빠진다. `kubectl apply -k apps/docs-site`로 복구하고 Runbook에 고정했다.

## 남은 위험

- `0.0.0.0` Port Forward는 TLS가 없는 임시 내부망 공개다. 외부 공개는 BLOCKED이며 OIDC/TLS Ingress가 필요하다.
- Flannel-only 환경에서 NetworkPolicy Object의 실제 패킷 차단은 기존과 동일하게 BLOCKED다.
- Token은 탭 단위 `sessionStorage`를 사용한다. 운영 인증은 OIDC/PKCE와 HttpOnly Secure Cookie로 교체해야 한다.
- HAMi 논리 GPU 값은 실제 성능 격리 보장이 아니다.

## 다음 단계 진행 가능 여부

포털 MVP의 내부 데모 운영은 가능하다. 외부/기관 통합 운영은 TLS, OIDC, 정책 집행 CNI가 준비된 뒤 진행해야 한다.
